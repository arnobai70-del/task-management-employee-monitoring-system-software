Reading (differences under ~20% between runs are noise on this host):
- 17 of 20 endpoints have p95 under 300 ms at 1000 employees / 60 days.
- attendance daily 60d: p95 ~290 ms, grows with the range; acceptable, watch with larger ranges.
- G-40 (fixed here) security dashboard 168h: p95 1755 -> 952 ms, p99 1970 -> 1086 ms.
  Cause: SecurityObservabilityService.GetDashboardAsync loaded EVERY audit row in the window into
  memory (105,479 rows for 7 days here) and filtered in C#. Growth was unbounded in window x
  activity. Now security events (auth.* and rate-limit rows: 20,982 here) and the newest 50
  privileged actions are queried directly; privileged and window totals are SQL COUNTs; the
  integrity fingerprint loads only its own capped prefix (ExportMaxRecords, default 50,000) as
  before. Rows materialised per request: 105,479 -> at most 20,982 + 50 + 50,000.
  Remaining cost is hashing the 50,000-row fingerprint on every dashboard load (unchanged design).
  Behaviour note: the auth./security. prefix match moved from C# OrdinalIgnoreCase to SQL
  (case-sensitive); every action name in the code base is lower-case.
- G-41 (proposal, not changed) audit log free-text search: p50 ~700 ms, p99 ~1.2 s under 4 clients.
  Cause: AuditLogService search uses lower(col) LIKE '%term%' on Action, TargetType, TargetId and
  IpAddress, so both the page query and the COUNT do a parallel sequential scan (EXPLAIN ANALYZE,
  single client: 117-138 ms per query at 300k rows; linear in table size).
  Trial on tm_perf with pg_trgm GIN indexes on the four lower() expressions:
    rare term (a target GUID): page 138 -> 6.9 ms, count 116 -> 6.1 ms
    IP 10.0.7.33:              page 131 -> 4.6 ms, count 128 -> 6.5 ms
    frequent term checked_in:  page 117 -> 1.2 ms, count 129 -> 77 ms
  Cost: 55 MB of indexes for a 46 MB table and four GIN updates on every audit insert, plus the
  pg_trgm extension in production. Needs an owner decision; trial indexes were dropped.
