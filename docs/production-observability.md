# Production Observability Runbook

This runbook covers the optional private observability overlay for the production TaskMonitoring server. It adds centralized API metrics and logs without exposing Prometheus, Loki, the OpenTelemetry collector or Grafana through the public Caddy application site.

## Architecture

```text
TaskMonitoring API
  -> OTLP metrics + ILogger logs
     -> OpenTelemetry Collector
        -> Prometheus-format metrics endpoint
           -> Prometheus
              -> alert-rule evaluation
              -> Grafana dashboards
        -> Loki native OTLP log ingestion
           -> Grafana log exploration
```

The API exports telemetry only when `Observability__OtlpEndpoint` is configured. The normal base production deployment remains valid without the overlay.

The production overlay uses pinned images:

- OpenTelemetry Collector Contrib `0.161.0`;
- Prometheus `3.15.0`;
- Loki `3.7.8`;
- Grafana `13.2.2`.

## Security boundary

All observability services live on a private Docker network. Collector OTLP ports are not published to the host. Grafana, Prometheus, Loki and the collector health endpoint bind to `127.0.0.1` by default.

Do not change `OBSERVABILITY_BIND` to `0.0.0.0` merely for convenience. Prometheus and Loki have no application-level authentication in this single-host overlay. For remote access, use an SSH tunnel to the loopback-bound Grafana port.

The Grafana administrator password is stored in the file configured by `GRAFANA_ADMIN_PASSWORD_SECRET_FILE`. It is generated by `init-production-secrets.sh` when the environment variable is present and the file does not yet exist. Store that secret in the organization's approved secret manager.

## API telemetry

The API emits:

- `taskmonitoring.api.up` — observable gauge with value `1` while the telemetry pipeline is running;
- `taskmonitoring.api.requests` — completed HTTP request counter tagged only with HTTP method and status class (`2xx`, `4xx`, `5xx`, etc.);
- `taskmonitoring.api.request.duration` — request-duration histogram in seconds using the same low-cardinality tags;
- `taskmonitoring.api.active_requests` — active-request up/down counter tagged by method;
- .NET runtime metrics from OpenTelemetry runtime instrumentation;
- structured `ILogger` events through OTLP.

Every HTTP response also receives a server-generated `X-Request-ID`. The same request ID is attached to the request logging scope. Client-supplied request IDs are not trusted or copied into the logging scope.

Request logs include method, path, status and duration but deliberately omit the query string so authentication or business query values are not copied into routine request logs. Health-check requests are measured but not written as per-request information logs.

## Start observability

Ensure the base production server is already healthy, then run:

```bash
bash scripts/production/observability-up.sh deploy/production/production.env
```

The script validates the combined Compose model, starts Collector/Loki/Prometheus/Grafana, recreates only the API container with its private OTLP endpoint, and requires all local health endpoints plus public API readiness to succeed.

Run end-to-end acceptance at any time:

```bash
bash scripts/production/acceptance-observability.sh deploy/production/production.env
```

Acceptance verifies that:

- collector, Prometheus, Loki and Grafana are healthy;
- the API remains ready;
- the API `up` and request metrics reach Prometheus;
- the committed Prometheus rules loaded successfully;
- API logs arrive in Loki through the OpenTelemetry collector;
- Grafana's internal database reports healthy.

## Access Grafana safely

With the default `GRAFANA_PORT=3000`, create an SSH tunnel from an operator workstation:

```bash
ssh -L 3000:127.0.0.1:3000 operator@server
```

Then open `http://127.0.0.1:3000` locally. Sign in with `GRAFANA_ADMIN_USER` and the independently retrieved Grafana admin password.

The provisioned **TaskMonitoring Operations** dashboard includes API telemetry state, request rate by status class, p95 request latency, active requests and centralized API logs. Prometheus and Loki are also provisioned as Grafana data sources for deeper investigation.

## Alert rules

Prometheus evaluates the committed rules in `deploy/production/observability/prometheus-alerts.yml`:

- API telemetry missing for three minutes — critical;
- collector scrape unavailable for two minutes — critical;
- Loki scrape unavailable for two minutes — warning;
- API 5xx ratio above 5% for ten minutes — warning.

These rules provide deterministic alert evaluation and are visible through Prometheus/Grafana. Delivery to an organization-specific pager, email, Slack/Teams or incident platform is intentionally not hard-coded because those destinations require organization credentials and routing policy. Configure the organization's approved Alertmanager/Grafana contact point before relying on automated paging.

## Retention and storage

Prometheus retention defaults to `15d` and can be changed with `PROMETHEUS_RETENTION`.

This single-node Loki configuration retains logs for seven days (`168h`) using its compactor and a Docker volume. Treat these local volumes as operational telemetry, not as a disaster-recovery copy. If longer retention or multi-host resilience is required, move Loki and Prometheus storage to the organization's managed observability platform rather than simply extending local-disk retention indefinitely.

## Stop observability

To stop the overlay while keeping its telemetry volumes:

```bash
bash scripts/production/observability-down.sh deploy/production/production.env
```

The script removes the observability containers, preserves named telemetry volumes, then recreates the API from the base production model so it no longer targets a stopped collector. API readiness is required before the script succeeds.

## Diagnostics

Combined stack logs:

```bash
docker compose \
  --env-file deploy/production/production.env \
  -f deploy/production/docker-compose.yml \
  -f deploy/production/observability.compose.yml \
  logs --tail=200 api otel-collector prometheus loki grafana
```

Never paste secret files, JWT values, database connection strings or Grafana passwords into incident tickets. Prefer request IDs, timestamps, status classes, audit event IDs and non-secret resource identifiers when correlating incidents.
