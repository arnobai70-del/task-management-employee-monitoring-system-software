1. Confirm backup is fresh: `bash scripts/production/backup-postgres.sh <env> pre-deploy` → record the printed path.
2. `bash scripts/production/deploy.sh <env>` — builds images, runs the one-shot `--migrate-only` container (API has `Database__AutoMigrate=false`), then starts API/web/Caddy.

4. Publish Windows release (signed bundle only): `bash scripts/production/publish-windows-release.sh --env <env> --bundle <dir>` (ZIP first, `release.json` last, immutable versions).

"Prometheus" alarms live in `deploy/production/observability/prometheus-alerts.yml` and need the private observability stack (`observability-up.sh`). Rule unit tests: `scripts/audit/prometheus-alerts.test.yml`.

Alert delivery: the owner chose the admin's PC (2026-10-14, "PC te"), not email or chat (G-47). Every in-app alarm above (Operations incidents) and every security alert now reaches the PC as a desktop notification when an admin turns on **Desktop alerts** in the Admin Web top bar (in the menu on phones) and allows notifications in the browser. A notification is shown only while the console is in the background (another tab or window), because the in-page toast shows otherwise; clicking it opens the Operations or Security Alerts page. The browser has to stay open with the console signed in, and notifications need HTTPS (production is served over HTTPS by Caddy).

The Prometheus-only alarms (API error rate, slow responses, telemetry down, retention lag) still show only in Prometheus/Grafana: there is no Alertmanager in the stack, so they do not reach the PC yet. Bringing them in needs an Alertmanager webhook into the API that raises an Operations incident (OPEN, follow-up).

## 4b. Team scoping for managers (G-27)
Employee lists, attendance, presence, monitoring activity, website work (list, progress, recent completions) and the website productivity report and timeline are limited to a user's own reporting line (themselves and everyone below them through the employee's **Supervisor**) unless one of the user's roles has the permission `employees.scope.all`.

- Upgrading changes nothing: migration `20261014170000_EmployeeScopeAll` grants `employees.scope.all` to every existing role that already had `employees.read`, `attendance.read`, `presence.read`, `monitoring.read`, `tasks.read`, `tasks.manage` or `reports.read`. SuperAdmin always has every permission.
- A role created after the upgrade does not get it automatically, so its users see only their own reporting line until it is granted.
- There is no screen to edit role permissions yet, so an operator changes it in the database (fictional role name shown):

```sql
-- Limit the "TeamLead" role to each lead's own reporting line:
DELETE FROM role_permissions
WHERE "RoleId" = (SELECT "Id" FROM roles WHERE "Name" = 'TeamLead')
  AND "PermissionId" = (SELECT "Id" FROM permissions WHERE "Code" = 'employees.scope.all');
-- Undo (let the role see every employee again):
INSERT INTO role_permissions ("RoleId", "PermissionId")
SELECT r."Id", p."Id" FROM roles r, permissions p
WHERE r."Name" = 'TeamLead' AND p."Code" = 'employees.scope.all'
ON CONFLICT DO NOTHING;
```

Users pick up the change at their next sign-in or token refresh (access tokens last `Jwt:AccessTokenMinutes`). Each lead's employee profile must have the right Supervisor set on their reports (Employees page).

What a role without `employees.scope.all` is limited to: employees (list, detail, edit, password reset), attendance and corrections, presence, monitoring activity, Website Work (lists, progress, edits, approve/reopen, attention report and actions), project tasks, the dashboard, daily attendance, workload, productivity and follow-up SLA reports, RDP/IP/website/survey-link assignments and their employee pickers, survey assignments and submissions, and realtime presence and Website Work events. Unassigned tasks and Website Work stay visible so a lead can pick them up.

Still organisation-wide on purpose: departments, projects, survey forms, the per-project and per-form report summaries, the supervisor, shift and project-member pickers (a lead's own manager can sit outside the team), operations incidents and the audit log. A role that also has `roles.manage` can give itself `employees.scope.all`, so keep that permission for administrators.

Realtime connections work out their scope when they connect; after a Supervisor change, a lead sees the new team's live events from their next reconnect or page reload.

## 5. Rollback
- Application: redeploy previous image tag/commit via `deploy.sh` with the previous checkout.
- Database: `bash scripts/production/restore-postgres.sh --env <env> --backup <path> --confirm-restore` (destructive — operator confirmation required). It replaces the whole `public` schema in one transaction, so tables added by a newer release are removed too and a failed restore changes nothing (G-49). After restoring a pre-deployment backup, deploy the matching older release, or rerun the migrator to move forward again. Rehearsed on 729 MB of fictional data: backup 32 s, restore 26 s (G-12 log). CI proves the path on every run with a >1 MB archive.
- Windows agents: previous version stays in the immutable archive; follow `scripts/windows/rollback-employee-windows.ps1` / central update controls.
